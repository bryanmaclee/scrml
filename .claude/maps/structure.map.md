compiler/src/ast-builder.js  — the AST builder. **THE ONE THING TO KNOW: `<engine>` / `<match>` / `<each>` are NOT `kind:"markup"` and carry NO `attrs` array.** The block splitter raw-captures each one and `buildBlock` RECONSTRUCTS its opener by regexing NAMED attributes out of the header text (`for=`, `initial=`, `on=`, `in=`, `of=`, `key=`, `as`, …). **An attribute nobody regexes for is silently DISCARDED at parse time** — the node has nowhere to hold it — and every downstream stage is innocent. That is exactly what happened to `if=` on those three for the language's whole life before S302: it parsed, vanished, and the element rendered unconditionally and permanently on a green compile. **Symptom → locus: "an attribute on a structural element has no effect and no diagnostic" is an ast-builder.js fact, not a codegen one.** The §17.1.2 template for adding one: `captureStructuralIfAttr(header, absStart, line, col, filePath, errors)` (:2705) — masks `${…}` bodies and quoted strings before the NAME search (so `effect=${ if (…) … }` can never be mistaken for the opener's own `if=`), requires a standalone `(^|\s)if\s*=` token (keeping `else-if=` out), captures the value depth-aware to the next attribute boundary, then **re-parses a SYNTHETIC `<x if=…>` opener through the SAME `tokenizeAttributes` + `parseAttributes` a markup opener uses** so the value object is byte-for-byte what `<div if=…>` produces — a second `if=` grammar is the defect #289 existed to remove. Offsets are rebased by −3 (the `<x ` prefix) so a diagnostic on the condition points at real source; `structuralHeaderAnchor(block, header)` (:2797) recovers the absolute offset/line/col the header slice lost, with a block-span fallback (an approximate caret beats a thrown builder). Node construction sites: `:15276` / `:17447` (match), `:16261` (each), `:17297` (engine). Also the fire site for the `E-CTRL-*`, `E-LOOP-*`, `E-SYNTAX-*`, `E-MW-*` and `E-FOREIGN-*` families.
